# Liquid Glass rendering-performance audit

Read-only audit. Scratch, scripts and raw data live beside this file (`lib.mjs`, `measure.mjs`, `ablate.mjs`, `flicker.mjs`, `extra.mjs`, `trace.jsonl`, `ablate.jsonl`, `extra.jsonl`, `flick/`).

## Build provenance (read first)

- **Valid data: every number below was taken against the fresh server the orchestrator said serves head `ea06da4`** (after the second restart; the runtime registers lenses from each surface's effect, and the page wash crossfades). I could not independently confirm the served commit; I only confirmed HTTP 200, `data-glass-engine` set, `scrollHeight < 20000` and styled body before each run.
- **Discarded: everything measured earlier** (old build, then stale `3bd38a8` with CSS returning 500: unhydrated pages, `scrollHeight` ~62000, `data-glass-engine` empty, 0 filters). Kept only for the record in `old-build-invalid/`, `old-build-invalid2/`, `pre-restart-3bd38a8/`. None of it is cited here. Earlier first-pass numbers (e.g. 20 ms/frame lens vs 4 ms no-glass) were also contaminated by concurrent server builds.
- Because of the wrap-up request, the full 4x-throttle fps matrix was **not** re-run on `ea06da4`; the table below is 1x CPU, one run per cell (trace pass). Run-to-run noise is large (about +-10 fps and +-30% draw time between identical cells), so read only large gaps.
- Headless Chromium, software GL, 4 cores: absolute draw times are far worse than a real GPU. Use ratios.

## 2. Surfaces, filters, maps, bundle (`ea06da4`)

- Simultaneous live backdrop-filter surfaces with non-zero size: desktop 10 (sidebar 232x884, queue 312x884, player 1176x72, bottom edge 1200x56, 5 toolbar capsules) plus top-edge `::before`/`::after` (opacity 0 until scrolled, still have a backdrop-filter declared). Approx 640k px of 1.3M viewport px (49%). Phone 5-6: tab bar 366x64, bottom edge 390x80, 2-3 toolbar buttons, **closed queue 366x448 (still carries a lens and a backdrop-filter)**. Phone about 228k of 329k px (69%) if the closed queue is counted.
- Lens filters: desktop 6 `<filter>` / 12 `<feImage>` (12 maps); phone 5-6 filters. Map PNG data URLs: desktop 37.8 KB total, phone 51.9 KB; sizes 36x36 .. 1176x72 (desktop), 366x448 (phone queue). Cache limit `FILTER_CACHE_LIMIT = 24`.
- Boot: 12 `toDataURL` calls, 7 ms at 1x, 11.4 ms at 4x (encode only; map generation JS is in the surrounding task, not separated). New popup: first user-menu open builds 1 filter (224x331), `toDataURL` 1.9 ms at 1x / 6.1 ms at 4x; second open reuses it (0 builds). A dialog on phone (390x844 = 329k px, under `MAX_LENS_AREA` 630k) builds a full-screen lens: 5.4 ms encode at 1x, 32.8 ms at 4x.
- JS: glass runtime chunk `2mjmu1smdqey6.js` 53.3 KB raw / 19.9 KB gz (shared with other code: contains registry, maps, sampler, runtime). Whole page `/` loads 2.04 MB raw / 625 KB gz of js+css; the single CSS chunk is 220.9 KB raw / 34.5 KB gz (glass.css is 924 lines of it).
- Idle (3 s, nothing playing): **rAF fires about 180 times (60 Hz) on `/`**, constantly. Source is not glass: `apps/web/components/player.tsx:141-150` loops `position.set(getPosition())` every frame forever, even paused or with nothing loaded. It keeps the main thread and compositor frame production awake, which matters more with 10 backdrop surfaces. 0 setTimeout and 0 setInterval at idle. Glass-owned idle listeners (registration counts): window `pointermove` 1, `pointerdown` 1, `deviceorientation` 1, `resize` 1 (lens-registry), `visibilitychange` 1 (not glass), 3 matchMedia `change`, `animationend`/`transitionend` per surface (13 each), 12 ResizeObserver observations, 2 MutationObservers (html attrs; body subtree childList+attrs).
- Not measured: `use-glass-artwork` colour extraction per navigation (needs a playing track; it is an 8x8 `drawImage`+`getImageData`, cached per URL in `artwork-sampler.ts`, so the cost is the 500px image fetch/decode plus the blurred ambient image, not the sampling).

## 4. Rebuild churn

- Desktop scroll: 0 filter adds, 0 `<filter>`/`<feImage>` attribute mutations. Registry is quiet.
- **Phone scroll: 22 (album) and 34 (browse) new filters built during one 5 s scroll** (27 and 40 in the no-backdrop variant too, so it is layout-driven, not paint-driven; cache limit 24 means evictions and repeated PNG encodes). Likely cause (not proven): the tab-bar minimize morph and toolbar resizes fire ResizeObserver per frame, so `schedule()` in `lens-registry.ts` clears the lens and rebuilds at each new settled size; `lensKey` includes exact width/height. Verify by logging `lensKey` per `createFilter`.
- `pointer-light.ts`: on every mouse `pointermove` (rAF) it calls `getBoundingClientRect()` on all registered surfaces and writes `--g-light` (style invalidation on every backdrop surface). Not benchmarked in this pass.

## 5. Load frame stability (3 s screencast per route/variant/scheme, `flick/`)

- **Lens swaps in after first paint.** `--g-lens-url` is set on 5-6 surfaces at about +350 to +700 ms after FCP (`lens-on` events at 879-1158 ms vs FCP 374-687 ms), spread over 150-300 ms. Surfaces first paint as frost and then change to refraction: a visible (small) material change on every load in lens mode. Same on phone (5 surfaces).
- **Ambient/wash pops in.** Dark `/` luminance steps 33 -> 48 -> 56 within 100 ms at about +700 ms (screencast time), light `/album` 235 -> 225 at about +640 ms. One-way steps (no reversals detected, no frame returned to the prior state).
- Theme: dark first-paint frames are dark (lum 11-35) from the first non-blank frame on lens runs; on `D___frost_dark` one white frame (lum 246) appears at +175 ms before the dark frame at +192 ms. It may be the pre-commit blank page rather than a theme flash; unresolved with a screencast alone (one occurrence in 12 runs, 0 in the other dark runs).
- `glass-surface-added` fires twice, once about 800-1200 ms after navigation start: surfaces mounting after hydration (queue/player), a layout-visible event of the new effect-based registration. No hydration errors captured; no layout-shift entries reported.
- No engine flip lens<->frost during load (`data-glass-engine` is set before first paint by the runtime evaluate; my html attribute observer did not attach in time, so this is inferred from lens-on events only, not directly observed).

## 7. Top cost centres (evidence)

1. Backdrop-filter surface count and area on desktop (all-off 12.4 vs baseline 32.2 ms/frame; about 49% of viewport px).
2. Ambient/page wash layer under the surfaces (-14 ms/frame, +17 fps when removed; phone: whole glass delta).
3. Lens on top of frost: +0 to +35% draw, plus first-load swap-in and per-new-size build (small).
4. Phone filter rebuild churn during scroll (22-34 builds per scroll).
5. Always-on 60 Hz player rAF loop (180 rAF per 3 s idle).
6. Closed queue on phone still holds a 366x448 lens + backdrop; top-edge pseudo-elements keep backdrop declarations while opacity 0.
